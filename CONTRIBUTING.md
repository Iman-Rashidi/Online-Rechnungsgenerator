# Contributing to Rechnio

Thank you for your interest in improving Rechnio! Contributions of all sizes are welcome, including bug reports, documentation improvements, accessibility fixes, and new features.

## Before you start

- Check the existing [issues](../../issues) to see whether the problem or idea has already been reported.
- For significant changes, open an issue first to discuss the approach.
- Keep changes focused and explain the reason for them.

## Reporting a bug

When opening a bug report, include:

- A clear, descriptive title.
- The steps needed to reproduce the problem.
- What you expected to happen and what actually happened.
- Your browser and device, where relevant.
- Screenshots or error messages, if they help explain the issue.

**Never include passwords, API keys, bot tokens, access tokens, or other private information in an issue.**

## Suggesting a feature

Feature requests should explain:

- The problem the feature would solve.
- The expected user experience.
- Any alternatives you have considered.

## Making a change

1. Fork the repository.
2. Create a branch for your change (for example, `fix/print-layout` or `feature/invoice-export`).
3. Make your changes in small, understandable commits.
4. Run the relevant checks and tests available in the project.
5. Update documentation when behavior or setup instructions change.
6. Push your branch to your fork.
7. Open a Pull Request against the repository's `main` branch.

## Pull Request checklist

Before submitting, please check that:

- [ ] The change has a clear purpose and description.
- [ ] Existing functionality has not been unintentionally broken.
- [ ] Relevant tests or checks have been run.
- [ ] Documentation has been updated when needed.
- [ ] No secrets, credentials, private data, or generated build artifacts were added.
- [ ] Any third-party code or assets are used in accordance with their licenses.

A maintainer may ask for changes or clarification before merging a Pull Request.

## Code and communication

- Be respectful and constructive.
- Prefer readable, maintainable code over clever shortcuts.
- Avoid unrelated formatting or refactoring in focused fixes.
- Do not submit code copied from sources whose license is incompatible with this project.
